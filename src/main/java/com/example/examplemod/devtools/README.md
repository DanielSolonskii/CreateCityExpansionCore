# Редактор рецептов для разработки

**Сверка состояния: 2026-11-04.** [Актуальный аудит CCEC/Cargo](../../../../../../../docs/audit-2026-11-04/README.md) описывает интеграцию 1.0.2.15. Ранее датированные результаты проверок ниже сохраняют свою дату; новый игровой/production прогон ими не подтверждается.

Проверено по коду **02.11.2026**. Общий статус: [CURRENT_STATE.md](../../../../../../../CURRENT_STATE.md),
[аудит](../../../../../../../docs/audit-2026-11-02/README.md).
Требуются Java 21 и рабочая dev-сборка с зависимостями из
[README_DEV.md](../../../../../../../README_DEV.md); редактор открывается внутри
Minecraft-клиента, а не отдельным приложением.

Команда: `/ccec recipes`. Только локальный оператор одиночного мира; выделенный сервер и гости LAN не допускаются.

1. Выберите корень проекта (папку с `build.gradle` и `src/main/resources`). Путь сохраняется в клиентском config.
2. Во вкладке «Создание» выберите тип кнопками «Тип». Для стандартных vanilla/Create типов используются готовые шаблоны без обхода рецептов мира при открытии.
3. Нажмите предмет в показанном инвентаре, затем нужную ячейку образца. Предметы не перемещаются и не расходуются. Для очистки ячейки 3×3 выберите пустой слот инвентаря. Слот справа от стрелки — результат.
4. Для выбранного ингредиента кнопка «Предмет / тег» перебирает доступные теги и возвращается к конкретному предмету. Для результатов теги запрещены.
5. Количество результата, альтернативы, компоненты, жидкости, время, нагрев, шансы и последовательности редактируются в JSON. Для крафта большего размера, например механического 5×5, задайте pattern/key в JSON. После ручных изменений используйте «Слоты из JSON».
6. Укажите уникальный ID `namespace:path`, проверьте JSON и подтвердите путь записи. Игра проверит рецепт штатным сериализатором перед сохранением.
7. Во вкладке «Редактирование» нажмите предмет в инвентаре и слот «Фильтр». ПКМ по предмету инвентаря — сокращённый способ поставить фильтр. Пустой образец очищает фильтр и список; поиск начинается только после установки непустого фильтра. JSON читается лишь для рецептов с нужным результатом. Рецепты перечисляются отдельно по ID, namespace и сериализатору. Для длинных списков есть полоса прокрутки справа, колёсико над списком и кнопки перехода сверху.
8. «Отключить рецепт» создаёт override с условием `neoforge:false`, не изменяя JAR исходного мода. Исходный JSON сохраняется внутри `_workbench_original`; выключенный рецепт виден как `[ОТКЛ]`. Его можно выбрать и снова сохранить для включения.

## Файлы и применение

Проектные результаты: `src/main/resources/datapacks/recipe_workbench/data/<namespace>/recipe/<path>.json`.

Копия этого пакета автоматически записывается в `datapacks/recipe_workbench` текущего мира, включается последней и применяется через штатную перезагрузку ресурсов сервера. Предыдущие версии редактируемых файлов сохраняются в `.recipe-workbench-backups` выбранного проекта. При ошибке reload интерфейс сообщает, что файл записан, но применение не подтверждено.

Запись атомарная; выход за каталог recipe и запись через символические ссылки запрещены. Существующие исходные JSON и JAR зависимостей не изменяются. Создание, замена и отключение используют единый приоритетный пакет.

Типы обнаруживаются по реально загруженным рецептам; обычные рецепты vanilla и Create поддерживаются через их собственные codecs. Особые динамические рецепты без постоянного выходного предмета могут не попадать в фильтр по результату; сложные и специальные форматы требуют JSON. Редактор не копирует приватный код JEI и не вводит зависимость от его версии.

## Удаление инструмента

При отдельной задаче удаления сначала выполните GitNexus impact и проверьте
регистрацию событий/текстовые ссылки. Пакет `devtools` содержит инструмент,
его экраны, модели черновиков и локальные проверки. Оставьте
`policy/RecipeWorkbenchPolicy.java` и `src/main/resources/datapacks/recipe_workbench`:
они обеспечивают постоянное применение созданных рецептов и отключений в
собранном моде. Для тестовых миров отдельно сохраняется локальный datapack,
действующий независимо от установленного инструмента. В аудите файлы инструмента
не удалялись.

## Проверка

Из корня репозитория:

```powershell
.\gradlew.bat jar checkRecipeWorkbench -I src/main/java/com/example/examplemod/devtools/check.gradle --offline
```

Задача добавляется через init script `check.gradle`; в обычном `check` она
автоматически не зарегистрирована. Проверка использует `mineVisualTest`
classpath и временные файлы, а не открытый игровой мир.

Проверки охватывают допустимый корень, пути вложенных рецептов, отказ на traversal и JSON постоянного отключения. Проверку интерфейса, диалога выбора папки и reload в игровом клиенте нужно провести вручную.

## Последовательная сборка

Для `create:sequenced_assembly` нажмите «Настроить этапы сборки». Общие настройки вынесены наверх: исходный ингредиент, промежуточный предмет, число повторений, результаты (можно добавлять/удалять) и их количество/вес.

Кнопки «← Этап / Этап →» переключают этап; «+ / − этап» добавляют и удаляют, «Выше / Ниже» меняют порядок. Кнопка с названием операции переключает добавление предмета, прессование, распиловку и заливку. Для каждого этапа черновики разных операций хранятся раздельно до закрытия формы. Промежуточный предмет автоматически используется на входе и выходе поддерживаемых этапов.

Нажмите образец в инвентаре и нужную ячейку. «Предмет / тег» применяется к последнему выбранному исходному или добавляемому ингредиенту. При добавлении предмета можно включить сохранение инструмента; у распиловки указать время в тиках; у заливки — ID жидкости/тега и объём в mB. Вес результата — относительный вес Create, не обязательно процент.

«Применить в черновик» возвращает изменения в основной JSON редактора; затем нужно отдельно сохранить рецепт, чтобы записать файл и применить его к миру. «Отмена» отбрасывает изменения формы. Неизвестные операции и сложные ингредиенты сохраняются; редактировать их можно в JSON.

## Механическая сборка (create:mechanical_crafting)

Для механической сборки сетка редактора расширяется до 9×9 (ячейки компактнее
ванильной 3×3). Клик по ячейке кладёт текущий образец; если такой же ингредиент
уже есть в key, ячейка переиспользует его символ, пустой образец очищает
ячейку. Форма меняется кнопками под сеткой: «+ Строка», «− Строка», «Шире»,
«Уже». Результат заполняется кликом по ячейке справа от стрелки. Существующие
символы key сохраняются при переключении рецептов.

Проверки модели этапов:

```powershell
.\gradlew.bat checkSequenceRecipe -I src/main/java/com/example/examplemod/devtools/check-sequence.gradle --offline
```

Эта задача также добавляется отдельным init script. Она проверяет сохранность
этапов/настроек при переключении типов и привязку промежуточного предмета;
запуск GUI, диалог выбора папки, реальные codecs зависимостей и reload мира
должны пройти отдельную игровую приёмку.

## Жидкости рецепта

Для типов, поддерживающих жидкости, в основном окне появляется кнопка
«Жидкости» (`create:mixing` — ингредиенты и результат, `create:compacting`
и `create:filling` — только ингредиенты, `create:emptying` — только результат).
В окне: добавление записи кнопками «+ Жидкость в ингредиенты» и
«+ Жидкость в результат», список существующих записей с иконкой ведра и объёмом,
«− Удалить выбранную» сверху.

Выбранная запись редактируется справа: ID жидкости или тега, объём в mB и
переключатель «Конкретная жидкость / Тег жидкости» (формат — `neoforge:single`
с полем `fluid` либо `neoforge:tag` с полем `tag`, как в фазе заливки
последовательной сборки). «Из ведра» подставляет жидкость ведра, взятого в
инвентаре в образцы; изменение применяется кнопкой «Применить».
«Применить в черновик» возвращает JSON в основной редактор, где рецепт нужно
сохранить отдельно.

Проверки модели жидкостей:

```powershell
.\gradlew.bat checkFluidRecipe -I src/main/java/com/example/examplemod/devtools/check-fluid.gradle --offline
```

Init script аналогичен остальным; GUI иregistry проверяются вручную в игре.

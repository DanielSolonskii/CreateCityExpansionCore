# Быстрый deploy CCEC

Из корня репозитория, PowerShell 7:

```powershell
.\Deploy.ps1
```

Одна команда собирает текущие исходники CCEC, готовит релиз из актуального подписанного канала, проверяет совместимость сохранений, предупреждает игроков за минуту, штатно обновляет сервер, публикует Windows и macOS ARM64, проверяет публичные подписи и совпадение JAR с сервером. После успешного обновления оставляет одну последнюю проверенную копию мира; резервные JAR и квитанции не удаляются.

Скрипт не спрашивает подтверждений: обычный запуск означает deploy. Для проверки без перезапуска и переключения каналов:

```powershell
.\Deploy.ps1 -DryRun
```

Требуются Node.js с поддержкой ES modules/fetch, PowerShell 7 (`pwsh`), Git, SSH/SCP, tar, настроенный SSH-доступ `root@186.246.28.214` и локальные Gradle-зависимости для offline-сборки. Ключ подписи остаётся на сервере. macOS публикуется с существующим серверным ARM64 overlay; Windows runtime на Mac не копируется.

## Что выбирается автоматически

- Следующий номер `alpha-X.Y.Z` и sequence — из текущего подписанного Windows manifest, а не исторической папки сборки.
- Версия самого мода — из `gradle.properties`; скрипт её не меняет. При необходимости новой версии мода обновите `mod_version` перед запуском.
- Клиентский профиль — только из проверенных публичных артефактов; локальные игроковые папки не импортируются. Используется последний доступный локальный object cache.
- На сервер попадает только CCEC. Остальные моды, конфигурации и игровые аргументы (включая автоподключение) сохраняются. Неожиданный diff останавливает запуск.
  Для явно запрошенного изменения модпака поддерживается `CCEC_DEPLOY_MODPACK`: путь к JSON с `schemaVersion: 1`, массивом `install` (`name`, `source`, `sha256`, `server`) и массивами `clientRemove`/`serverRemove` (`name`, `sha256`). Файлы и удаления закрепляются по SHA-256, перечень копируется в квитанцию запуска; обычный запуск без переменной по-прежнему обновляет только CCEC. При продолжении используется сохранённый перечень. Клиентские моды не следует добавлять на сервер.
- Если клиентский профиль и установленный серверный JAR уже совпадают с кандидатом, результат `NO_CHANGES`: нет перезапуска и бессмысленного нового релиза.

## Краткий вывод и продолжение

На экран выводятся только этапы, итог и путь к квитанции. Полный журнал и состояние находятся в `build/quick-deploy/<run>/deploy.log` и `state.json` (не входят в Git).

```powershell
.\Deploy.ps1 -Resume "build/quick-deploy/<run>"
```

Используйте точную команду из вывода. Продолжение берёт сохранённый JAR этого запуска, а не пересобирает новые изменения. Повторно проверяются локальный кандидат и совместимость с сервером; изменение профиля останавливает продолжение. Для новых исходников нужен новый обычный запуск.

После сбоя публикации проверяется, не успел ли Windows-канал переключиться: уже опубликованный кандидат не публикуется повторно. Ошибка macOS сохраняет успешные сервер/Windows и при продолжении повторяет Mac-шаг. Автоматический откат работающего сервера не выполняется.

Если процесс прервался внутри серверного шага, результат может быть неопределённым. Скрипт остановится и потребует проверить `deploy.log`, сервер и remote backup state; он не станет вслепую снова останавливать сервер. После жёсткого завершения также может остаться `build/quick-deploy/deploy.lock`: сначала убедитесь, что PID из файла больше не работает. Активную блокировку удалять нельзя.

Этот инструмент выпускает игровой профиль, а не установщик лаунчера, backend или Telegram-бота. Сборка и readiness не заменяют игровую приёмку интерфейсов и физической доставки.

Проверки инструмента:

```text
node --test platform/launcher/scripts/quick-deploy.checks.mjs
python -B platform/launcher/scripts/test_quick_deploy.py
```

Низкоуровневые операции и ручной rollback остаются в [Release.ps1](../launcher/scripts/Release.ps1); контракт — [controlled release workflow](controlled-release-workflow.md).

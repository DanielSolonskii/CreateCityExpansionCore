## Эффективность тестов

В CI находится один workflow с командой `./gradlew build`. В корневой `check` включены предметные Java-проверки, в том числе экономика Cargo, а в платформе есть JUnit, Vitest, Rust и отдельные регрессии релизных скриптов. У Cargo уже проверяется идемпотентность выплаты. Для дефекта после аварии нужна связка двух сохранений. Это хороший пример того, где стоит расширить существующий тест предметным сценарием. [Workflow](../../.github/workflows/build.yml#L30) · [Привязка доменных тестов](../../build.gradle#L849) · [Повторный расчёт](../../src/mineVisualTest/java/com/example/examplemod/cargo/center/CargoCenterCheck.java#L47)

- В рабочем дереве обнаружено 40 методов `@GameTest` в 14 классах. Их игровой запуск не входит в штатный `build`. Энергетика и часть других наборов требуют отдельных init-скриптов и тестового окружения. Высокую ценность имеют тесты на демонтаж с добычей и переходы Cargo на настоящем серверном тике. [GameTest-конфигурация](../../build.gradle#L93) · [Энергетика](../../tools/industrial-energy-gametest.init.gradle)
- Из 97 тестовых файлов `*Check.java` (`mineVisualTest` и `knowledgeTest`) у восьми проверок обнаружен только отдельный вход через Gradle-скрипт. Это `KnowledgeSyncCheck`, `PaintAimCheck`, `PaintGripCheck`, `PaintNozzleCheck`, `BoundaryPresentationCheck`, `MineWorkMotionCheck`, `PanelTextureCoordinatesCheck` и `CommunityCheck`. В корне отдельно включён `checkCommunityV2`. Новый функционал может пройти CI без запуска проверок именно его набора. [База знаний](../../tools/knowledge-check.init.gradle) · [Community](../../tools/check-community.gradle) · [Community V2](../../build.gradle#L670)
- Часть UI-проверок сравнивает буквальный текст Java. Например, `WorldMapPanelLifecycleCheck` принимает наличие проверки `this.map == null` в теле метода за защиту других обращений. В изолированной копии в начало `mouseScrolled` добавили разыменование карты перед проверкой. Исходный и изменённый варианты выдали одинаковый результат — `PASS: 47`. Эквивалентное переименование поля, напротив, может его сломать. Здесь полезнее отдельно тестировать порядок событий открытия, закрытия и первого кадра. [Шаблон исходного текста](../../src/mineVisualTest/java/com/example/examplemod/client/screen/WorldMapPanelLifecycleCheck.java#L73) · [Проверка условия](../../src/mineVisualTest/java/com/example/examplemod/client/screen/WorldMapPanelLifecycleCheck.java#L321)
- Корневая конфигурация подключает 77 специальных задач `check…`, из них 76 используют `JavaExec`. Даже с готовыми классами это отдельные старты JVM. Совместимые быстрые проверки можно объединить в один тестовый процесс, сохранив отдельные среды для проверок, которые меняют глобальное состояние. Для PR полезно запускать тесты изменённого компонента платформы, быстрые проверки ресурсов и headless-проверки. Дорогие GameTest-сценарии с реальными модами можно вынести в отдельный запуск. Backend `test` исключает PostgreSQL, для проверки реальной СУБД есть задача `postgresTest`. [Backend](../../platform/backend/build.gradle#L33) · [Launcher](../../platform/launcher/package.json) · [Telegram-бот](../../platform/telegram-bot/build.gradle#L20)
